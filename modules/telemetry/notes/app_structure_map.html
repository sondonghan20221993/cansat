앱 구조 맵

cFS 앱 4개가 각각 어떤 파일로 나뉘고, 어떤 루프를 돌며, 무엇을 구독하고 발행하는지. 4개 앱은 같은 골격을 공유하지만 루프 방식이 두 갈래로 갈리고, 그 차이가 각 앱의 성격을 결정한다.

앱 · 4개 구현 코드 · ~10,400 줄 시리얼 점유 · 2개 앱 영속 상태 파일 · 3개 앱

01공통 골격 — 파일이 곧 레이어

4개 앱 모두 같은 5개 파일 역할로 나뉜다. cFS 표준 앱 템플릿을 따르되, 이 프로젝트는 도메인 로직을 전부 _utils.c에 모으는 규칙을 일관되게 지킨다.

<app>.c
수명주기 — Main() / Init(). 파이프 생성, MID 구독, 상태 파일 로드, 그리고 CFE_ES_RunLoop 본체.
<app>_dispatch.c
분기 — 들어온 SB 메시지의 MID를 보고, 명령이면 FcnCode까지 확인해 핸들러로 넘긴다. 길이 검증도 여기.
<app>_cmds.c
명령 핸들러 — NOOP / RESET_COUNTERS 같은 표준 명령과 앱 고유 명령의 진입점. 실제 일은 utils에 위임.
<app>_utils.c
도메인 로직 — 파싱·검증·상태머신·프레임 조립·영속화. 앱 코드의 대부분이 여기 있고, 유닛테스트도 이 파일을 겨냥한다.
config/*.h
계약과 상수 — MID 값, 메시지 구조체, 튜닝 파라미터. 코드를 안 고치고 바꿀 수 있는 건 여기 있는 값들뿐이다.
코드 무게중심 — 구현 줄 수의 약 절반이 _utils.c 한 파일에 몰린다(mavlink_bridge 2,511줄 / lora_tdm 1,152줄 / cfs_core 1,202줄 / uplink 953줄+cmds 511줄). 테스트가 utils 함수 단위로 붙어 있어 지금은 작동하지만, 파일 하나가 계속 커지는 방향이라는 건 알고 있을 만하다.

02루프가 두 갈래인 이유

"SB 메시지가 오면 처리한다"와 "정해진 시각에 무선을 쏜다"는 요구가 다르다. 전자는 이벤트 구동, 후자는 시간 구동이라 루프 모양이 갈린다.

유형 A — SB 대기 + 타임아웃 주기작업

mavlink_bridge · cfs_core · uplink
while (RunLoop) {
    Status = ReceiveBuffer(pipe, 200ms);
    if (SUCCESS)   TaskPipe(msg);      // 메시지 처리
    else if (TIMEOUT) ServiceXxx();    // 주기 작업
    else           앱 종료;            // 파이프 오류
}
  • 메시지가 있으면 즉시 처리, 없으면 200ms 만에 깨어나 자기 일을 한다
  • 주기 작업 내용: FC 시리얼 서비스(bridge) · 헬스 판정과 앱 감시(core) · 상태 발행과 UDP 폴링(uplink)
  • 바쁜 대기가 없고, 트래픽이 몰려도 파이프 깊이(16~32)까지 버퍼링된다

유형 B — 고정 사이클 (시간 구동)

lora_tdm
while (RunLoop) {
    OS_TaskDelay(100ms);
    RunCycle();
}
RunCycle() {
    while (ReceiveBuffer(pipe, POLL)) …  // 논블로킹 드레인
    RunTx();                              // DL2 송신
    RunRxWindow();                        // 50ms 수신 창
    UpdateLinkState();
}
  • SB를 기다리지 않는다 — 쌓인 걸 POLL로 훑고 바로 무선 스케줄로 넘어간다
  • 무선 타이밍이 SB 트래픽에 흔들리면 안 되기 때문 (TDM 창이 밀리면 지상이 응답할 자리를 잃는다)
  • 파이프 깊이 50으로 다른 앱(16~32)보다 깊다 — 한 사이클에 몰아서 비우는 구조라서

타이밍 상세는 notes/tdm_timing_map.html에 시간축으로 펼쳐 두었다.

03앱별 내부

mavlink_bridge_app

유형 A · FC UART 점유
  • 주기 작업 ServiceSerial() — MAVLink 바이트 파싱, 재연결(1s 간격), HEARTBEAT 송출(1s)
  • 구독 CMD 0x18A0 · SEND_HK · ROUTE_UPDATE 0x190B · CONFIG 0x190E
  • 발행 FC 상태 5종(0x1905~0x1909) · BRIDGE_HK 0x08A0
  • 고유 상태 미션 업로드 상태머신, readback 백오프, ActiveResumeIndex, FcBaseMode
  • 파이프 깊이 32 — FC 상태를 가장 자주 다루는 앱
utils 2,511줄 · app 175 · dispatch 76 · cmds 20

cfs_core_app

유형 A · 감독자
  • 주기 작업 — 캐시 만료 판정, 헬스 종합, 앱별 HK 두절 감시와 재시작(각 최대 3회)
  • 구독 14종으로 가장 많다 — FC 상태 4종 + 앱 HK 3종 + 명령 6종 + 미션 readback
  • 발행 SYSTEM_HEALTH 0x1904 · ROUTE_SNAPSHOT 0x1913 · HK 0x08C0
  • 고유 상태 미션 경로 캐시, 재시작 누계, 마지막 FaultCode (파일 영속)
  • 만료는 Pi 도착시각 기준, FC 타임스탬프는 순서·재부팅 감지용으로만
utils 1,202줄 · app 227 · dispatch 108 · cmds 18

uplink_app

유형 A · 명령 관문
  • 주기 작업 — 상태 텔레메트리 발행, 개발용 UDP 경로 폴링
  • 구독 CMD 0x18D0(LoRa가 전달) · SYSTEM_HEALTH · BRIDGE_HK · EXEC_RESULT 0x1912
  • 발행 class별 명령 MID 7종 + UPLINK_STATUS 0x190A
  • 고유 상태 마지막 수락 seq, 부팅 카운터, 단명부팅 streak (파일 영속)
  • 명령 핸들러가 커서 유일하게 _cmds.c가 500줄대로 두껍다
utils 953줄 · cmds 511 · app 140 · dispatch 95

lora_tdm_app

유형 B · LoRa UART 점유
  • 사이클 SB 드레인 → RunTx() → RunRxWindow() → 링크 판정
  • 구독 10종 — FC 상태 5종 + 헬스 + UPLINK_STATUS + CONFIG + DIAGNOSTIC + ROUTE_SNAPSHOT
  • 발행 LINK_STATUS 0x1911 · HK 0x08E0 · 그리고 수신 UP 프레임을 0x18D0으로 전달
  • 고유 상태 DL2 프로토콜 버전(v1/v2), waypoint readback 페이지 진행, 링크 카운터
  • 유일하게 app.c가 두껍다(593줄) — 시리얼 열기/닫기와 사이클 로직이 여기 있어서
utils 1,152줄 · app 593 · dispatch 188 · cmds 57

04누가 무엇을 구독하는가

앱 간 결합은 오직 이 표다. 같은 MID를 여러 앱이 구독하는 자리(CONFIG, ROUTE_UPDATE)가 이 시스템에서 가장 조심해야 하는 지점 — 한 앱의 해석이 바뀌면 나머지도 같이 봐야 한다.

MID메시지발행구독
0x1905~08FC 상태 (EKF_LOCAL / ATTITUDE / GPS_RAW / EKF_STATUS)bridgecore, lora
0x1909FC_SYS_TIME (GPS UNIX epoch)bridgelora
0x1904SYSTEM_HEALTHcorelora, uplink
0x190BROUTE_UPDATEuplinkcore + bridge (병렬)
0x190ECONFIG_CMDuplinkcore + bridge + lora (scope 분기)
0x190C / 0x190FRECOVERY_CMD / MODE_CMDuplinkcore
0x1910DIAGNOSTIC_CMDuplinklora(target 0) / core(target 1)
0x1912EXEC_RESULTcore, bridge, lorauplink
0x1913ROUTE_SNAPSHOT (readback)corelora
0x18D0UPLINK_CMD (UP 프레임 전달)lorauplink
0x08A0 / 0x08C0 / 0x08D0 / 0x08E0앱별 HK각 앱core (감시·재시작 판단)
구조체는 공유, 상수는 재선언 — 여러 앱이 주고받는 메시지 구조체는 shared_msgs/에 단일 진실로 두지만, MID 값이나 enum 상수는 각 앱 config/에 독립 재선언하는 게 이 프로젝트의 관례다. 필드 추가는 항상 구조체 끝에만 — 기존 오프셋이 움직이면 무선 프레임 호환이 깨진다.

05재시작을 견디는 상태

앱 3개가 전원이 나가도 살아남아야 하는 값을 파일로 남긴다. 방식은 세 앱이 동일하다 — 매직 + 버전 + 체크섬 + 원자적 rename.

앱남기는 것
cfs_core헬스 상태, 앱별 재시작 누계, 마지막 FaultCode, 런타임 CONFIG
uplink마지막 수락 seq, 부팅 카운터, 단명부팅 streak
lora_tdm다운링크 프로토콜(v1/v2) 선택
  • 경로는 상대경로 cf/ — 절대경로 /cf/는 OSAL 가상경로 매핑을 안 거쳐 Pi 실파일시스템에서 조용히 실패했던 이력이 있다
  • 체크섬 불일치 파일은 로드하지 않고 기본값으로 시작한다
  • 부팅 카운터는 다운링크 프레임에 실려 나가 지상이 기체 재부팅을 감지하는 근거가 된다
