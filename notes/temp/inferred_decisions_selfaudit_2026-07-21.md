# 추론 기반 구현 자기점검 (2026-07-21)

> "구현했을 때 명확하지 않거나 모호해서, spec 근거 없이 AI 추론으로
> 채워진 부분이 있는지" 확인 요청에 따른 자기 감사.
> **이 문서의 항목은 전부 "재검토 대상"이지 확정된 설계가 아님.**

---

## [높음] A-1. RunTx의 UFB 리셋 제거 → 스티키 UFB (부작용 확인됨)

**변경**: 커밋 `073a680` — `RunTx()`가 매 사이클 `PendingUplinkFeedback`을
`UFB_OK`로 리셋하던 것을 제거.

**근거**: 없음. spec에 "판정값을 언제까지 유지할지"에 대한 규정이
없었고, 제가 "다음 명령 전까지 유지"가 맞다고 판단해 결정.

**확인된 부작용**: 리셋 지점이 이제 성공 포워딩 2곳
(`lora_tdm_app_utils.c:502`, `:591`)뿐이고, CRC_FAIL 경로 6곳
(`:415/433/441/452/464/639`)은 포워딩으로 이어지지 않음
→ **CRC_FAIL/SEQ_FAIL/STATE_BLOCKED가 다음 "성공한" 명령까지 무한 래치**.

문제의 핵심은 **DL2 프레임의 `ufb` 바이트에 대응 uplink seq 태그가
없다는 것**(`lora_protocol_v2_spec.md:47` — 필드는 `ufb u8` 단독).
지상 GUI(`plugin.js` `armPendingCommand`)는 명령 POST 직후 무장하고
**그 다음에 처음 도착한 UFB를 그 명령의 판정으로 간주**하는데, 어느
명령에 대한 응답인지 구분할 방법이 프로토콜에 없음.

| | 변경 전 | 변경 후(현재) |
|---|---|---|
| 래치 여부 | 매 200ms OK로 리셋 | 다음 성공 명령까지 유지 |
| 잘못 읽힐 때 결과 | 가짜 **OK** (= 오늘 발견한 그 버그) | 이전 명령의 판정이 **오귀속** |
| 파생 피해 | "적용됨" 오표시 | CRC_FAIL 오귀속 시 **3회 자동 재전송 유발** |

→ **오답의 종류를 바꿨을 뿐 근본 해결이 아님.** 진짜 해법은 UFB에
대응 uplink seq를 함께 실어 지상이 상관(correlate)할 수 있게 하는
프로토콜 확장이며, 그건 제 판단으로 할 게 아니라 결정이 필요함.

**재검토 필요**: 현 상태 유지 / 롤백 / seq 태그 추가 중 택일.
→ 관련 spec: `lora_protocol_v2_spec.md` §4(DL2 포맷),
`lora_tdm_app_behavior_spec.md` §10(UFB 정책, 제가 쓴 내용이라 근거 아님)

## [중] A-2. `UFB_STATE_BLOCKED = 3` 신설 — 값·이름·매핑 범위 전부 제 선택

**변경**: 커밋 `9358647`.

제가 임의로 정한 것:
- **값 `3`** — 단순히 다음 빈 번호
- **이름 `STATE_BLOCKED`** — spec에 없던 명칭
- **매핑 범위** — `REJECT_STATE(11)` 하나만 매핑. 나머지 거부 코드
  (`FAILED(4)`, `REJECT_CLASS(6)`, `REJECT_LENGTH(7)`, `ROUTE_MISS(8)`,
  `REJECT_ROUTE(9)`, `REJECT_CHECKSUM(12)`, `REJECT_VIEWPOINT(13)`)는
  **여전히 UFB로 전달되지 않아 지상에선 OK와 구분 불가**

이건 무선 프로토콜(DL2 wire format) 확장이라 지상/기체 버전이 어긋나면
해석이 갈림. 지금은 제가 양쪽을 동시에 고쳐서 맞지만, 버전 협상 장치는 없음.

**재검토 필요**: 나머지 거부 코드도 UFB로 표현할지, 아니면 UFB를
"대분류"로 두고 상세는 별도 필드로 뺄지.

## [중] A-3. SEQ_FAIL 매직넘버 3→10 — "이름이 맞고 숫자가 틀렸다"는 판단

**변경**: 커밋 `04d8f99`.

`REJECT_SEQUENCE`라는 **이름**을 authoritative로 보고 숫자를 enum
실제값(10)에 맞춤. 반대 해석(원저자가 값 3=`ROUTED`를 의도)은 의미상
성립하지 않지만, **원저자 의도를 실제로 확인한 것은 아님**.

→ 근거는 충분하다고 보나, "AI가 둘 중 하나를 골랐다"는 사실은 기록.

## [중] A-4. 지상국 `downlink_protocol` 범위를 0..1로 제한 — 기체보다 엄격

**변경**: openMCT 커밋 `0c7f9b2`.

- 기체: `(Value != 0U) ? 1U : 0U` — **0이 아니면 뭐든 수용**
- 제가 지상에 넣은 제한: `(0, 1)`

오늘 실제로 값 `2`를 보냈고 기체가 정상 수용했는데, 이제 **지상에서
2는 400 에러로 거부됨**. 기존에 되던 게 안 되게 만든 동작 변경이며,
"0/1 외 값은 의도 불명확하니 막는 게 맞다"는 건 제 판단.

**재검토 필요**: 기체 검증에 맞춰 지상도 느슨하게 할지, 아니면
기체 쪽을 0/1로 엄격화할지(양쪽 일치시키는 방향).

## [중] A-5. `PARAM_BOUNDS` 전반 — 지상이 기체 상수를 손으로 복제

지상국 `PARAM_BOUNDS`의 min/max는 기체 헤더
(`default_*_internal_cfg_values.h`)를 읽어서 **복사**한 값.
동기화를 강제하는 장치는 주석뿐이라, 기체 상수가 바뀌면 지상이
조용히 어긋남 — `system_wide_reaudit`의 F-4(죽은 config 상수)와
같은 계열의 함정을 **제가 새로 하나 더 만든 셈**.

## [중] A-6. `bridge/` legacy 판정 — 2개는 제 추론 + **자기모순 있음**

- `lora_uplink_bridge.py` → spec에 "대체됨" 명시 있음 (근거 확실)
- `lora_telemetry_bridge.py`, `mavlink_uart_bridge.py` → **제 추론**
  ("앱이 해당 시리얼을 독점 소유하므로 동시 실행 불가")

**자기모순**: 같은 라운드에서 `tools/mission_upload_diag.py`는
*"cFS 우회 직접 시리얼 진단용, 정상"* 이라며 그대로 뒀는데,
`mavlink_uart_bridge.py`도 **똑같이 cFS를 우회하는 시리얼 진단
도구**임(cFS 정지 상태에서 쓰면 충돌 없음). 같은 성격에 다른 판정을
내림 — 기준이 일관되지 않았음.

**재검토 필요**: `mavlink_uart_bridge.py`를 `tools/`로 되돌릴지,
아니면 `mission_upload_diag.py`도 같은 기준으로 재분류할지.

## [낮음] B-1. Pi `config.txt`의 `init_uart_clock=48000000` 잔존

세션 초반 baud 문제 조사 중 "UART 클럭 정밀도" 가설로 추가했으나
**그 가설은 기각됨**(실제 원인은 파서 STX 버그 + mission-install 누락).
"무해하고 마진에 도움될 수 있다"는 제 판단으로 되돌리지 않고 뒀음.

기각된 가설의 잔재가 설비에 남아있는 상태 — 되돌릴지 결정 필요.
(현재 Pi 전원 off라 실제 잔존 여부 미확인)

## [낮음] B-2. MAVLink 파서 STX 재진입 수정 방식

"`WAIT_STX` 상태에서만 STX를 프레임 시작으로 인식" 방식을 채택.
MAVLink 구현체들의 표준적 접근이지만, 대안(길이 기반 재동기,
CRC 실패 시 1바이트 shift 재탐색 등)과 비교 검토한 기록은 없음.
현재 실측상 정상 동작(손실률 0%)이라 우선순위는 낮음.
