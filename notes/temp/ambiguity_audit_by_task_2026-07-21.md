# Task별 모호성 점검 (2026-07-21)

> `BACKLOG.md` 항목별로 "spec에 명시가 없어서 구현자가 임의로 정해야
> 하는 지점"을 착수 전에 미리 찾은 것. **답을 내린 게 아니라 결정이
> 필요하다는 걸 표시한 것** — 각 항목은 실제 착수 시 사용자 확인 필요.

## BL-01 — 재전송 중복 오탐 차단

- **새 결과코드의 번호/이름 미정**: enum이 13(`REJECT_VIEWPOINT`)까지
  차 있어 `14`가 다음 빈 값. 이름도 `DUPLICATE`/`REJECT_DUPLICATE`/
  `RETRANSMIT` 중 무엇으로 할지 spec에 없음
- **replay(진짜 재생공격, `seq < last`)와 우리 재전송(`seq == last`)을
  UFB에서 같은 코드로 묶을지 분리할지 불명**. 지금 계획대로면 후자만
  구제되고 전자는 여전히 `SEQ_FAIL`인데, 그게 맞는 정책인지는 미정
- **부트스트랩 예외**(`AcceptedCount==0`이면 무조건 수락)와의 상호작용:
  기체가 막 재시작한 직후 지상이 옛 seq로 재전송하면 그게 그대로
  "새 명령"으로 수락됨 — BL-03(부트 카운터)이 오기 전까지는 이 구멍이
  남아있음, 문서화만 해둘지 지금 막을지 미정

## BL-03 / BL-12 / BL-13 — 다운링크 seq 동봉 + 부트카운터 + 모듈러 비교

- **v1 텍스트 프로토콜엔 seq를 넣을 자리 자체가 없음** (오늘 확인).
  `SH,%lu,%lu,%u,%u,%u,%u\n` — 필드 6개 전부 용도가 정해져 있고 seq
  자리가 없음. **v2(DL2)에만 넣고 v1은 그대로 버그 상태로 둘지, v1도
  같이 고칠지, 아니면 이 참에 v1을 deprecate할지 결정 안 됨**
  (`LORA_TDM_APP_PARAM_DOWNLINK_PROTOCOL` 기본값이 아직 0=v1이라
  실사용중인 경로)
- **DL2 필드 삽입 위치 미정**: 현재 레이아웃은 `Buf[0]`(magic)~`Buf[41]`
  (satellites)까지 빽빽이 정해져 있음. `ufb_seq`/`boot_count`를 어디에
  넣을지(끝에 추가 vs 기존 필드 재배치), flags 비트를 더 쓸지 새 바이트를
  늘릴지 미정
- **boot_count 폭 미정**: 8/16/32비트 중 무엇으로 할지. 재부팅이
  드문 이벤트라 8비트(256회)로도 충분할 수 있으나 근거 문서 없음
- **모듈러 윈도우 절반값(`0x8000`) 자체가 제 임의 선택** — 더 좁게
  잡으면(예: `0x1000`) replay 방어는 세지지만 "정상적인 큰 시간차
  desync"를 더 못 봐줌. 실제 운용 패턴(초당 명령 빈도, 최대 유휴시간)
  근거가 없어 숫자를 못 정함
- **DL2/v2가 아직 "기본값 0=v1"이라는 점** — 이 작업을 하면서
  v2를 기본값으로 승격할지도 별도 결정 사항(spec엔 "단계적 전환"만
  있고 승격 조건이 명시 안 됨)

## BL-04 — 링크 상태 전이 EID (LOST/DEGRADED/RESTORED)

- **플래핑 시 이벤트 폭주 방지 정책 없음** — 5Hz 사이클에서 링크가
  경계값 근처를 오가면 매 사이클 이벤트가 날 수 있음. 히스테리시스
  (예: N 사이클 연속 조건 충족 시에만 전이) 도입 여부/N값 미정
- **"복구(RESTORED)"의 기준점**: DEGRADED→CONNECTED만 RESTORED인지,
  DISCONNECTED→CONNECTED도 RESTORED로 부를지 spec에 안 갈림
  (`lora_tdm_app_behavior_spec.md`엔 "LinkState → CONNECTED 복구"로만
  적혀 있어 출발 상태 구분이 없음)
- **부팅 직후 최초 진입도 "전이"로 칠지**: `LastAckTimestampMs==0`인
  최초 상태에서 CONNECTED로 처음 들어갈 때 RESTORED 이벤트를 낼지
  (의미상 "복구"가 아니라 "최초 연결"이라 다른 취급이 자연스러울 수
  있으나 정해진 바 없음)
- **`SUB_ERR_EID`/`PIPE_ERR_EID`/`SB_SEND_ERR_EID`를 넣을 때 실패 후
  동작 정책 미정**: 이벤트만 내고 계속 진행할지, 재시도할지, 앱을
  포기시킬지 — 특히 초기화 구독 실패는 현재 `return Status`로 앱
  전체가 죽는 경로라 이벤트 추가만으로 충분한지 확인 필요

## BL-08 — 실행결과(EXECUTED) 회신 채널

가장 모호함이 큰 항목:

- **새 MID를 대상 앱마다 각각 만들지, 공용 하나로 만들지 미정**.
  대상이 `cfs_core_app`/`mavlink_bridge_app`/`lora_tdm_app` 3곳인데
  각자 다른 결과 구조(예: `MAVLINK_BRIDGE_CONFIG_RESULT_*`,
  `cfs_core_app`는 아직 그런 세분화된 결과코드 자체가 있는지 미확인)
- **`uplink_app`이 회신을 얼마나 기다릴지(timeout) 미정** — 대상 앱이
  안 답하면(크래시/헹) 영원히 PENDING인지, N초 후 자동 실패 처리할지
- **회신-대기 상태를 유지하는 동안 새 명령이 오면 어떻게 할지**
  (같은 seq만 추적하는지, 여러 명령을 동시에 pending 시킬 수 있는지)
- **`mission_app_runtime_spec.md` §18.4.6.4가 이미 "완료"라고 적어둔
  걸 정정할지, 진짜로 완성해서 그 표기를 맞출지** — BL-05와 얽힘,
  방향(spec 낮추기 vs 코드 올리기)이 안 정해짐

## BL-09 — cfs_core_app RECOVERY 명령 실제 연결

- **새 CMD_MID 이름/값 미정** (`PARSER_RESET_CMD`/`SERIAL_RECONNECT_CMD`
  가칭) — 기존 `MAVLINK_BRIDGE_APP_CMD_MID`의 FcnCode로 얹을지, 별도
  MID를 새로 만들지 두 방식 다 가능하고 정해진 게 없음
  (`mavlink_bridge_app_cmds.c`는 현재 `NOOP`/`RESET_COUNTERS`/
  `MISSION_QUERY` 3개뿐이라 4번째 FcnCode 추가 여지는 있음)
- **크로스앱 명령에도 §18.11.1 권한검증이 적용돼야 하는지 불명확**.
  이건 지상→uplink_app→cfs_core_app 경로가 아니라
  **cfs_core_app→mavlink_bridge_app 내부 경로**라 원래의 권한 모델
  (지상 사용자 인증)이 적용 대상인지 자체가 애매함
- **`RESTART_UPLINK`/`RESTART_LORA`를 enum에 추가할 때, 그 값이
  기존 `RECOVERY_ACTION_*` 번호 체계 어디에 들어갈지**(끝에 추가 vs
  의미상 재배치) — 재배치하면 이미 배포된 지상 도구/GUI와 어긋날 위험

## BL-11 — UFB 코드표 전체 확정

- BL-08(EXECUTED)의 설계가 먼저 나와야 여기서 매핑할 소스 값이
  정해짐 — 즉 이 항목은 **독자적으로 모호한 게 아니라 BL-08 결과에
  종속**
- **거부 사유 8종을 전부 별도 UFB 코드로 뺄지, "대분류 REJECT +
  상세는 별도 필드"로 압축할지** — u8 하나로는 종류가 많아지면
  부족해질 수 있어 구조 자체를 다시 볼 필요

## BL-16 — downlink_protocol 범위

- **"기체를 엄격화"와 "지상을 완화" 중 뭘 택해도 파급 효과가 다름**:
  엄격화하면 미래에 값 2,3...을 다른 프로토콜 버전으로 쓸 여지가
  원천 차단됨. 완화하면 지금 넣은 안전장치(PARAM_BOUNDS)의 취지가
  약해짐 — 트레이드오프 자체가 spec에 없는 새로운 결정

## BL-19 — 죽은 config 상수 정리

- **`LORA_TDM_APP_LORA_BAUDRATE`를 실제로 연결할지, 아니면 상수를
  삭제하고 "57600 고정, 설정 불가"로 명시할지** — mavlink_bridge처럼
  가변 baud를 지원할 실제 필요가 있는지(LoRa 모듈 스펙상 다른 baud로
  운용할 계획이 있는지)가 spec에 없어서 "죽은 코드 제거"와 "기능
  추가" 중 뭘 할지 결정이 안 됨
- **`STREAM_REACQUIRE_TIMEOUT_MS`**: 원래 의도가 뭐였는지 커밋 이력
  추적이 필요 — 단순 삭제 전에 "이거 없어서 실제로 문제가 된 적
  있는지" 확인 필요(제가 아직 안 함)

## BL-23 (openMCT) — 재전송 큐 타이머

- **타이머를 넣을 때 반이중 슬롯과 어떻게 맞물릴지 구체안 없음** —
  "다운링크 수신 시에만 flush"를 "N초마다도 flush"로 바꾸면, 원래
  "다운링크 직후 슬롯에 맞춰 보낸다"는 설계 의도(정렬)와 타이머
  주도 전송이 충돌할 수 있음. `uplink_lora_test_status.md` §4가
  이 이슈를 예견했으나 구체적 해법까지는 안 적혀 있음
