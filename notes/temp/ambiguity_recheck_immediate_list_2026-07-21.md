## 모호성 있는 항목

### BL-17 — LoadState() 실패 이벤트
- **새 EID 번호 필요**: `uplink_app_eventids.h`는 1~7까지 사용 중
  (`STARTUP`~`AUTHZ_BLOCK`), 8이 다음 빈 번호 — 재사용 가능한 기존
  EID 없음(확인 완료)
- **첫 부팅(파일 없음, `ENOENT`)과 진짜 손상(체크섬 불일치)을 같은
  이벤트/심각도로 묶을지 구분할지 미정.** 첫 부팅은 정상 상황이라
  ERROR로 찍으면 매 최초기동마다 오탐성 에러 로그가 남음 — INFO로
  구분 처리할지 결정 필요

### BL-19 — 죽은 config 상수 정리
- **`STREAM_REACQUIRE_TIMEOUT_MS`의 원 의도가 커밋 이력에서 안 잡힘**
  (`git log -S`로도 도입 커밋을 못 찾음 — 애초에 정의만 되고 실제
  기능이 구현된 적이 없을 가능성). "삭제"와 "기능 구현" 중 뭘 할지는
  이전 감사(`system_wide_reaudit`)에서 이미 미결정으로 남겨둔 항목 —
  재확인해도 여전히 근거 부족, 삭제 전 실제 필요성(SET_MESSAGE_INTERVAL
  재요청 로직과 관계있어 보임) 확인 권장

### BL-26/27/28 — 매직넘버 C↔Python 교차검증
- 확인 결과 **모호성 낮음**: C쪽 상수가 전부 단순
  `#define NAME VALUE` 형태(`CFS_CORE_APP_PARAM_MIN_MS` 등)라 정규식
  파싱으로 Python 테스트가 값을 뽑아 비교하는 게 어렵지 않음.
  기존 `test_lora_downlink_decoder.py`의 C↔Python 교차검증 패턴을
  그대로 재사용 가능 — 착수 시 설계 고민 적음

### BL-07 — cfs_core_app_command_execution_gap.md 갱신
- 문서의 RECOVERY 항목이 "무조건 리셋"이라고만 적혀 있는데 실제
  코드는 이미 switch문으로 세분화돼 있음(`RESET_COUNTER`만 동작,
  나머지는 로그) — **어느 시점 기준으로 "갱신"할지**: 지금 상태
  그대로 반영만 할지, 아니면 BL-09(RECOVERY 실제 연결) 완료 후
  한 번에 갱신할지 순서 문제. 두 번 고치는 걸 피하려면 **BL-09
  완료 후 갱신이 효율적** — 지금 "바로 진행 가능"으로 분류했지만
  실질적으로는 BL-09 뒤에 오는 게 나음
